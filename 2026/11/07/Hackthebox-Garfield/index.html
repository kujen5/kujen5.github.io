Hackthebox: Garfield

Overview

Garfield is a hard-difficulty Windows machine from Hack The Box with the following scenario: enumerate writable AD objects with bloodyAD -> notice scriptPath is writable on l.wilson -> drop a password-reset .bat in SYSVOL and abuse the logon script -> l.wilson resets l.wilson_adm (ForceChangePassword) -> WinRM on DC01 + user flag -> l.wilson_adm can write the RODC Administrators group -> add ourselves and create a fake machine account -> set RBCD on RODC01 -> S4U2self/S4U2proxy to forge a cifs/RODC01 ticket as Administrator -> tunnel to the internal RODC subnet with chisel, bind port 445 unprivileged via a user namespace + socat, and bypass the +8h clock skew with libfaketime -> psexec for SYSTEM on RODC01 -> mimikatz lsadump::lsa /inject to pull the krbtgt_8245 AES256 key -> modify the RODC Password Replication Policy to allow Administrator -> forge an RODC golden ticket and run the Kerberos Key List Attack to recover the Administrator NT hash -> Pass-the-Hash -> root.

This one is a proper AD chain. The whole box is built around a Read-Only Domain Controller (RODC), so if you’ve never played with RODC golden tickets or the Key List Attack before, this is a great box to learn them on. We’re also handed credentials up front (j.arbuckle : Th1sD4mnC4t!@1978), so it’s assumed-breach style from the start.

Foothold - Logon Script Abuse

So here’s the plan. The scriptPath attribute tells Windows which script to run when a user logs in, and it’s resolved relative to the NETLOGON/SYSVOL scripts folder. If I can write a script to SYSVOL and point l.wilson’s scriptPath at it, then whenever l.wilson “logs in” (the box simulates logons), my script runs as l.wilson.

And why do I care about running code as l.wilson? Because l.wilson has User-Force-Change-Password over l.wilson_adm — that’s a really common pattern where a user and their admin counterpart are linked. So my script is just going to reset l.wilson_adm’s password.

The nice thing is this is a completely self-contained payload — no reverse shell, no racing a netcat listener. The script just resets a password and we’re done. I threw three different reset methods in there so whichever one the host supports fires:

Enumeration as l.wilson_adm

Before diving into anything fancy, let me see what this new account is and what it can do:

SeMachineAccountPrivilege is enabled, which means l.wilson_adm can add new computer accounts to the domain (up to the default 10). File that away — we’re going to need a machine account for RBCD in a minute.

Now let me look at the computers in the domain:

There’s our RODC. DNS resolves RODC01.garfield.htb to 192.168.100.2, which is an internal subnet we can’t reach directly from the VPN. The only host that can reach it is DC01 itself, which is dual-homed (192.168.100.1 internally + 10.129.26.128 on our side). So anything we do against the RODC later is going to have to go through a tunnel pivoting off DC01.

The other key finding here is that l.wilson_adm has write access on the “RODC Administrators” group. This is the pivot. That group isn’t local admin on the RODC — what it grants is the delegated right to modify the RODC computer object in AD, including its msDS-AllowedToActOnBehalfOfOtherIdentity attribute. In other words, membership in that group lets us set up RBCD against RODC01.

RBCD Against RODC01

The path to the RODC is Resource-Based Constrained Delegation. The plan:

  1. Add l.wilson_adm to the RODC Administrators group so we can write the RODC’s delegation attribute.
  2. Create a fake computer account (we have SeMachineAccountPrivilege).
  3. Configure RBCD so our fake computer is trusted to delegate to RODC01.
  4. Use S4U2self/S4U2proxy to request a service ticket to RODC01 impersonating Administrator.

Getting the S4U Ticket (and the clock skew problem)

Problem two: binding 445 needs CAP_NET_BIND_SERVICE, and I can’t setcap without root:

So the trick is: inside the namespace, run a socat that forwards 127.0.0.1:445 -> 127.0.0.1:1445 (our chisel tunnel), then run impacket against 127.0.0.1:445. I wrapped the whole thing in a script:

Dumping the krbtgt_8245 AES256 Key

The whole reason we went after the RODC is its krbtgt_8245 account. That’s the per-RODC krbtgt key that signs the TGTs the RODC issues. If we get its key, we can forge an RODC golden ticket, and then use the Key List Attack against the real DC to pull out the Administrator hash.

Let me try secretsdump first to dump the RODC’s NTDS over VSS:

Notice that nearly every account comes back as 31d6... — that’s the empty-password NT hash, i.e. a placeholder. That’s expected: an RODC only stores secrets for accounts whose passwords have actually been replicated to it (its Password Replication Policy), which initially is just RODC01$ and krbtgt_8245. So 445aa4221e751da37a10241d962780e2 is the real krbtgt_8245 NT hash.

Problem is, if you try to forge the RODC golden ticket with that RC4/NT hash, the modern Server 2019 DC rejects it with KRB_AP_ERR_BAD_INTEGRITY — it validates the PAC signatures using the strongest key available, which is AES256, and an RC4-signed PAC fails. So we need the AES256 key, and secretsdump -just-dc over VSS doesn’t hand us Kerberos keys for this account. Time for mimikatz.

Upload mimikatz to the RODC through the same SMB tunnel and run lsadump::lsa /inject against krbtgt_8245 (I wrapped it in a .bat redirecting to a log, because passing nested quotes through psexec’s cmd /c is painful):

There’s our AES256 key: d6c93cbe006372adb8403630f9e86594f52c8105a52f9b21fef62e9c7a75e240.

Modifying the RODC Password Replication Policy

One more prerequisite before the golden ticket. For the Key List Attack to actually return Administrator’s key material (instead of just a session key), Administrator has to be allowed to replicate to the RODC. That’s controlled by two attributes on the RODC object:

  • msDS-RevealOnDemandGroup — the allow list.
  • msDS-NeverRevealGroup — the deny list, and deny always beats allow.

Let me look at the current policy:

Administrator is a member of BUILTIN\Administrators, which sits in the NeverReveal (deny) group — so even if we allow Administrator, that explicit deny wins. We need to both add Administrator to the allow group and wipe the deny group. Since l.wilson_adm has write on the RODC object via the RODC Administrators group, we can do both:

Setting msDS-NeverRevealGroup with no values clears it entirely. Administrator is now allowed to be replicated to the RODC.

RODC Golden Ticket + Key List Attack

Now the payoff. I’ll forge an RODC golden ticket as Administrator using the krbtgt_8245 AES256 key, then send it to DC01 with the Key List Attack to extract the real Administrator hash.

One heads up: use a recent Rubeus. Rubeus 2.2 builds the PAC for RODC golden tickets in a way the modern DC rejects with BAD_INTEGRITY even when the key is correct — 2.3.3 from SharpCollection signs it properly. Grab that one.

Forge the ticket:

The key part is /rodcNumber:8245 — that encodes the RODC branch ID into the ticket’s kvno field, which tells the full DC to validate the PAC signatures with krbtgt_8245‘s keys rather than the main krbtgt.

Now the Key List Attack. I feed that forged TGT back to DC01 with /keyList /service:krbtgt/garfield.htb. The DC treats it as a legitimate RODC request, replicates Administrator’s password material (which we just allowed via the PRP), and hands back the NT hash:

There it is — Administrator NT hash: EE238F6DEBC752010428F20875B092D5.

Worth noting why this attack works and the more obvious ones don’t: lsadump::dcsync from SYSTEM on the RODC fails with 0x2105 because RODC$ doesn’t have full replication rights, and lsadump::netsync fails with STATUS_NO_TRUST_SAM_ACCOUNT because RODC machine accounts don’t speak the regular netlogon trust protocol. The Key List Attack is a legitimate part of the Kerberos protocol that DCs implement specifically so RODCs can fetch keys for accounts in their PRP — we’re just signing the request with krbtgt_8245 ourselves.

Final Thoughts

Garfield is a great box if you want to actually understand RODCs rather than just read about them. The foothold is a clean, self-contained logon-script abuse, but the real meat is everything around the RODC — RBCD to get a foothold on it, then the golden ticket + Key List Attack to walk back up to the real Administrator. The supporting tricks (libfaketime for the clock skew, chisel for the pivot, and the user-namespace + socat dance to bind 445 without root) are the kind of thing that are annoying the first time and second nature after. Fun box, thanks for reading!

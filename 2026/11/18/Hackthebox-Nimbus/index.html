Overview

Nimbus is a hard-difficulty linux machine from Hack The Box that starts with a Server-Side Request Forgery (SSRF) vulnerability in a job-submission feature that fetches arbitrary URLs for us. By octal-encoding the IP of the instance metadata service we bypass the “metadata endpoints are blocked” filter and steal temporary STS credentials for the nimbus-web-role. That role can only list SQS queues, but the queue URL leaks the internal hostname of a LocalStack container named floci. Using the SSRF a second time with a decimal-encoded IP, we sweep the Docker bridge, locate LocalStack on port 4566, and read the worker source straight out of its unauthenticated S3. The worker deserialises jobs with the unsafe YAML loader and runs an attacker-controlled script field through python3 -c, so sending a message to the queue gives us a reverse shell as worker and user.txt. Inside the container we find the internal LocalStack runs with IAM enforcement off, giving us unauthenticated access to CodeBuild, which we abuse with a privilegedMode build and a writable /proc/sys/kernel/modprobe usermode-helper trigger to execute code as host root and read root.txt.

SSRF → Instance Metadata

First the honest attempt, just to see the guard rail:

Blocked, as advertised. But the filter is doing string/range matching on the IP as written, and IPv4 has more than one spelling. The classic move is to re-encode 169.254.169.254 so it doesn’t look like itself. Octal does the trick — each octet with a leading zero: 169 → 0251, 254 → 0376, giving 0251.0376.0251.0376. We also have to satisfy the “must point to a .yaml file” check, so we bolt a junk ?a=test.yaml on the end; the metadata service ignores the unknown query param and the validator only looks at the suffix.

Worth remembering.

Reaching Internal LocalStack (SSRF, round two)

The role can list a queue but can’t read S3, and we really want to know what the workers actually do with these jobs. The S3 data lives on that internal floci box. Our SSRF runs from inside the network, so it can reach internal hosts the role’s IAM can’t — but first we have to actually find floci.

Trying the hostname through the SSRF gets us nowhere (it doesn’t resolve on the fetcher side), and the plain private IP is blocked by the same policy as before. So we lean on the same encoding trick used for the metadata service, this time with decimal IPs, and sweep the Docker bridge range for anything answering LocalStack’s health endpoint on 4566. The instance was 10.0.1.42, but LocalStack containers usually sit on a 172.x bridge, so we start there:

There it is — 172.18.0.2:4566 (decimal 2886860802) is floci. The full health output confirms it’s a fat LocalStack instance with basically every service turned on:

codebuild being “running” catches our eye immediately (keep that in mind), but first things first — we want the source. The nimbus-web-role couldn’t GetObject on the public endpoint, but the internal LocalStack doesn’t ask us for credentials at all. The bucket will be something dev-flavoured, and nimbus-dev-artifacts is the obvious guess for where a job worker’s code would be staged. Path-style S3 read, through the SSRF, via the decimal IP:

This is the whole foothold sitting in thirty lines. The web front-end loudly parses with safe_load and promises “no code execution at submission time” — but the worker on the far side of the queue does the exact opposite. It pulls each message off nimbus-jobs, runs it through yaml.load(..., Loader=yaml.Loader) (the unsafe full loader), then takes a script field straight out of the job and feeds it to python3 -c. And the one permission our stolen role does have is the ability to write to that queue. So this is remote code execution by design — we just have to send the worker a job.

Privilege Escalation → root.txt

CodeBuild in LocalStack backs its builds with real Docker containers on the host. The dangerous part is that a project can request privilegedMode: true, which gives the build container a fat capability set, a shared kernel with the host, and write access into /proc/sys/.... That’s not a build setting, that’s a host-root primitive waiting to be used. The plan:

  1. Create a privileged CodeBuild project (image floci/floci:latest, the same image floci uses, so it’s present locally).
  2. Inside the build, abuse the kernel usermode-helper mechanism. When the kernel hits a binary format it doesn’t recognise, it calls the program named in /proc/sys/kernel/modprobe — and in a privileged container that file is writable and resolves against the host filesystem through the overlay upperdir. So we point it at our own script and then trigger it by executing a file with bogus magic bytes (\xff\xff\xff\xff). The kernel can’t find a handler → runs our script → as host root.
  3. One catch: floci’s image entrypoint tries to drop privileges by checking id first. We smuggle a shell function in through the BASH_FUNC_id%% environment variable so id reports uid 0 and the entrypoint trusts it.

There’s a subtlety worth calling out: the build container itself can’t route to our tun0, so the exfil can’t come from inside the build. That’s fine — the payload runs on the host via the usermode helper, and the host can reach us. So the host-side script is what phones home with the flag.

The Chain, Start to Finish

Key Takeaways

  • IP allow/deny lists that match on the string are not a control. Octal, decimal, and other IPv4 encodings walked straight past the “metadata endpoints are blocked” filter. If you must protect IMDS, enforce IMDSv2 and block at the network layer — don’t regex the URL.
  • A trust boundary follows the data, not the service. The web tier validated with safe_load and bragged about it; the worker on the other side of the queue used the unsafe loader and python3 -c on a user field. Validating at one hop means nothing if the next hop trusts the same data blindly.
  • Two endpoints, two IAM postures, one privesc. The public LocalStack proxy enforced IAM; the internal floci:4566 had ENFORCE_IAM=false and accepted junk credentials. Once you have code execution on the inside, that internal endpoint is an open door to every service it runs — here, CodeBuild.
  • privilegedMode: true is root on the host. Shared kernel plus a writable /proc/sys/kernel/modprobe plus the usermode-helper trigger is a clean, reliable container escape, and BASH_FUNC_* smuggling neuters entrypoints that “drop privileges” by trusting id.

That was it for Nimbus, hope you learned something new!
